● Final Year Project — Data Science / AI Track

Building Ustaad G, one feature at a time.

This is your complete build map for the USTAAD G home-services app — a voice-first, AI-powered platform connecting users with service providers (electricians, plumbers, painters and more). For every feature you listed, you get a flow diagram, the exact tools to learn, where to get data, which tool is the smart pick, and the traps to watch for. Read it like a lab manual, not a spec sheet.

Features covered: 14
Guiding rule: free / local tools first, API only when nothing else works
Audience: you, on day one of building your first app

Now let's talk about actually finishing this well.

Sit back for a second — this part is the difference between a project that gets a passing grade and one a company remembers.

1. Don't build all 14 features. Build 4, brilliantly.

I know the feature list is exciting — it reads like a real startup pitch. But you are one student with one semester (maybe two). If you try to build all 14, you'll end up with 14 things that half-work, and in your defense, a panel member will click one button, watch it fail, and that's the memory they leave with. Instead, pick a "core loop" of 4–5 features that tell one complete story end-to-end: for example — (1) Voice-powered search in Urdu/English/Roman Urdu → (2) Multimodal Damage Assessment → (3) Smart Dynamic Pricing → (4) Proof-of-Work Verification → (5) Fake Review Detection. That's a full journey: a user speaks a problem, uploads a photo, gets a fair price, gets verified work, and leaves a trustworthy review. Build the rest as "designed but not implemented" — show the diagrams and architecture in your report, and say clearly "this is planned for the next phase." Examiners respect honesty about scope far more than a pile of half-broken features.

Why this matters to companies: A recruiter or FYP judge does not measure you by feature count. They measure you by whether what you built actually runs, whether you can explain every decision behind it, and whether the code is clean enough that another engineer could pick it up. Four working, well-explained features beat fourteen fragile ones, every time.

2. The order you should learn things in (since you've never built an app before)

  1. Python fundamentals — if you're not already comfortable, spend 1–2 weeks here. Everything downstream depends on this.
  2. Data handling — Pandas and NumPy. You'll use these constantly to clean and shape data before any model sees it.
  3. Classical Machine Learning — Scikit-learn (regression, classification, clustering, Isolation Forest). Most of your "smart" features (pricing, badges, anomaly detection) use this, not deep learning — and that's fine. Simpler models that you understand deeply are more impressive than complex ones you can't explain.
  4. One deep learning framework — PyTorch is the current industry standard (companies hire for PyTorch far more than TensorFlow now). You'll need it for vision (damage assessment, proof-of-work) and voice (speech-to-text, translation).
  5. APIs and backend — Learn FastAPI (Python). It is the modern standard for serving ML models as web services, and it's what real companies use today, not Flask.
  6. A simple frontend/app shell — you don't need to be a frontend expert. Use Flutter (one codebase for Android + iOS) or React Native. If time is short, even a working web app (React or plain HTML/JS) that "acts like an app" is acceptable for an FYP — the AI/data-science work is what's being graded.
  7. Database — PostgreSQL. Learn basic schema design: users, providers, bookings, reviews, service_tickets.
  8. Deployment basics — Docker (so your project runs the same on any machine, including the judges'), and a free-tier host (Render, Railway, or Hugging Face Spaces for your ML models).

3. Treat this like real data science, not "vibe coding"

For every model you build, follow the same loop every time: define the question → collect/simulate data → clean it → explore it (EDA, with real charts) → try a simple baseline model first → try a better model → measure it properly with the right metric → write down why it works or doesn't. Keep every one of these steps visible in a Jupyter notebook per feature. This notebook, more than the final app, is often what convinces a technical judge you actually understand data science — not just that you copy-pasted a tutorial.

4. Data is your biggest real obstacle — plan for it early

You don't have real user data yet (no app has users on day one). Don't let this block you. Use this order of preference: (1) small amounts of real self-collected data (record your own voice, photograph appliances in your house, ask 5–10 friends to help), (2) public datasets that are close enough to adapt (Kaggle, Mozilla Common Voice, COCO), (3) carefully simulated/synthetic data that follows realistic rules (for bookings, pricing, fraud patterns). Always tell the judges exactly which data is real and which is synthetic — this honesty is expected and respected in data science, not penalized.

5. Keep the API rule you set for yourself — it's a good one

Sticking to free/local/open-source tools wherever possible is exactly the right instinct. It forces you to actually understand the tool instead of just calling someone else's endpoint, it means your project runs even without internet or a paid key during your defense, and it is genuinely more impressive to a company — anyone can wire up an API key, but fine-tuning a model or writing your own detection logic shows real skill. Reserve API calls only for the handful of places in this document marked as "API needed" — those are the places where building it yourself would take months a student doesn't have (like production-grade Urdu translation at scale).

6. Version control and documentation from day one

  • Put your project on GitHub from the very first line of code — not at the end. Commit often, with clear messages ("add pricing regression model", not "update").
  • Write a README for every module explaining what it does, how to run it, and what it needs.
  • Keep a short weekly log (even 3 sentences) of what you tried, what worked, what didn't. This becomes gold when you write your final report and when you're asked "why did you choose X over Y" in your defense — you'll have the real answer, not a guess.

7. Think about privacy — this app touches sensitive personal data

Voice recordings, home photos, and location data are personal and sometimes sensitive. Even for an FYP demo, show that you've thought about this: mention in your report that recordings/photos would be stored securely, access-controlled, and deletable by the user on request. You don't need a full legal framework — just showing awareness of this is something judges and companies specifically look for now, especially with AI products.

8. How to demo it so it lands

  • Prepare one clean, rehearsed end-to-end demo video (5–7 minutes) as a backup — live demos fail, especially with voice/network involved.
  • Show the model's mistakes too, briefly, and explain how you'd fix them. This signals maturity far more than pretending everything works perfectly.
  • Have one slide per feature with the flow diagram (you already have these in this document) — it makes your defense far easier to follow.

9. The one habit that will make the biggest difference

Build the smallest possible working version of a feature first — even if it's ugly — before making it smart. A pricing feature that just adds up hardcoded numbers, working end-to-end today, is more valuable than a beautiful regression model that isn't connected to anything yet. Get the pipe connected first, then make the water cleaner. This single habit is what separates finished student projects from abandoned ones.
