01 User Registration and Login ▾
1 · How it flows
Open app → pick role: User or Provider
→
Fill signup form (name, email, phone, password)
→
Backend hashes password, checks duplicates
→
Save user in database
→
Send OTP/email verification
→
Login → server issues JWT token
→
Token unlocks dashboard/app screens
2 · Tools & concepts (explained simply)
FastAPI (Python)Free

This is your backend "brain" — the program that receives the signup form data from the app, decides what to do with it, and talks to the database. Why FastAPI: it's Python (which you already know as a Data Science student), it's fast, modern, and every company today expects to see it or Flask/Django on a resume.

bcryptFree

Never store a password as plain text — if your database is ever leaked, every account is compromised. bcrypt is a small library that scrambles ("hashes") the password into unreadable text before saving it. When the user logs in later, bcrypt checks if the typed password matches the scrambled one, without ever un-scrambling it.

JWT — JSON Web TokenFree

After login, the server needs a way to remember "this device belongs to this logged-in user" without asking for the password on every single click. A JWT is a small signed digital ticket the server hands to the app; the app shows this ticket on every future request instead of the password.

PostgreSQLFree

This is where all user and provider accounts actually live — like a giant, very organized spreadsheet that your backend can query instantly. PostgreSQL is chosen over a plain file because it enforces rules (no two accounts with the same email) and scales to thousands of users.

SMTP / free email API (only for sending the verification email)API needed here

Sending a real email to a real inbox requires talking to a mail server — this genuinely can't be built entirely by yourself without huge effort, so a small free-tier service (e.g. Gmail SMTP or SendGrid free tier) is the one honest place to use an external service in this feature.

3 · Alternatives & what to actually pick
Recommended: self-built JWT + bcrypt (with Google OAuth added on top)

Firebase Authentication is faster to set up, but it hides all the logic inside Google's servers — an interviewer can't tell if you understand authentication or just plugged in a service. Building your own login system with bcrypt + JWT, and then additionally offering "Sign in with Google" (a well-known, genuinely necessary use of OAuth), shows both fundamentals and awareness of modern UX. Auth0 is enterprise-grade but costly and overkill for a student project.

4 · Edge cases to plan for
  • Duplicate email signup — check the database before creating a new account and show a clear error.
  • Weak passwords — enforce a minimum length and character mix on the form before it even reaches the backend.
  • OTP/email link expiry — give the verification code a 10–15 minute lifespan and allow "resend."
  • Forgot password — build a reset-link flow, don't just leave this out.
  • Wrong role selected — let users switch or contact support if they signed up as the wrong type by mistake.
  • Repeated failed logins — temporarily lock the account after 5 failed attempts to block brute-force guessing.
02 Service Request Creation ▾
1 · How it flows
User types problem description (+ optional photo)
→
Text classifier model predicts category
→
User confirms or edits the category
→
Request saved to database
→
Sent to the matching engine (feature 03)
2 · Tools & concepts (explained simply)
scikit-learn text classifier (TF-IDF + Logistic Regression / Naive Bayes)Free

This is the actual Data Science piece of this feature. You collect example sentences ("my tap is leaking", "no power in the kitchen") labelled with their correct category, and train a small model to guess the category from new text automatically. TF-IDF turns words into numbers the model can understand; Logistic Regression/Naive Bayes then learns the pattern.

Image upload & storageFree/local

Letting a user attach a photo of the broken tap helps the provider understand the job before arriving. Store images on your own server's disk folder for the student version (completely free); only move to a cloud storage service later if you deploy publicly and need reliability.

PostgreSQL table: service_requestsFree

Stores the description, chosen category, photo path, user id, location, and timestamp — this becomes the single source of truth the rest of the app (matching, booking, history) reads from.

3 · Alternatives & what to actually pick
Recommended: scikit-learn classifier as the core, with a HuggingFace transformer as a "bonus" upgrade

Simple keyword matching (if description contains "leak" → plumbing) is easy but looks unimpressive on a Data Science project — there's no learning involved. A trained scikit-learn classifier shows real ML work with almost no cost. If you want an extra "wow" section for your report, add a small pretrained transformer model (e.g. DistilBERT via HuggingFace, run locally, no API fee) and compare its accuracy against your simpler model — this comparison itself is great report content.

4 · Edge cases to plan for
  • Vague description ("something's broken") — if the model's confidence score is low, ask the user a clarifying question instead of guessing.
  • Overlapping categories — some problems fit two categories (e.g. water damage from electrical fault); allow multi-category tagging.
  • Non-English or mixed-language text — detect language first and fall back to manual category selection if unsupported.
  • No matching category exists — always keep an "Other / Not sure" category with human review.
  • Spam/fake requests — rate-limit how many requests one account can submit per hour.
03 Nearby Service Provider Matching ▾
1 · How it flows
Browser asks for GPS location (permission)
→
If typed address instead: geocode to lat/long
→
Query DB: providers within X km, matching category
→
Distance calculated for each candidate
→
Shortlist shown on map + list
2 · Tools & concepts (explained simply)
Browser Geolocation APIBuilt-in "API," free

This is a feature already built into every phone/laptop browser — with the user's permission, it hands your webpage the current GPS coordinates. There's no way to get real GPS location without it, so this is a genuinely necessary "API" (and it costs nothing).

Nominatim (OpenStreetMap geocoding)Free API, only if needed

If a user types an address instead of sharing GPS, you need to convert "123 Main Street" into coordinates. Building your own global address database yourself is unrealistic for a student project, so this is the one honest place to lean on a free, no-signup-required API.

Haversine formulaFree — pure math

A simple mathematical formula (a few lines of Python) that calculates the straight-line distance between two GPS points on Earth's curved surface. You write this yourself — no library or API needed.

PostGIS (PostgreSQL geospatial extension)Free

Instead of pulling every provider from the database and calculating distance one by one in Python, PostGIS lets the database itself answer "give me all providers within 5km" instantly using spatial indexing — this is exactly how real companies do it at scale, which is a strong point to mention to evaluators.

Leaflet.js + OpenStreetMap tilesFree, no billing

This draws the actual visual map in the app, with pins for nearby providers. Unlike Google Maps, it needs no credit card or API key limits, which matters a lot for a student budget.

3 · Alternatives & what to actually pick
Recommended: PostGIS + Leaflet/OpenStreetMap

Google Maps Platform is the most "well known" name but requires billing setup even for a free tier, which is risky for a student who might forget to set spending limits. Mapbox is a good middle-ground alternative with generous free tiers and nicer default styling if you want a more polished look. PostGIS specifically is worth highlighting in your report because many real logistics and ride-hailing companies use exactly this technology — mentioning it signals you understand production-grade geospatial systems.

4 · Edge cases to plan for
  • No providers within radius — automatically widen the search radius step by step rather than showing an empty screen.
  • User denies location permission — fall back to manual address entry.
  • Inaccurate GPS indoors — show an approximate radius circle rather than a falsely precise pin.
  • Stale provider location — ignore providers whose last location update is older than, say, 30 minutes.
  • Provider in a different city than listed — validate location updates against a reasonable travel speed to catch GPS glitches.
04 Smart Provider Ranking ▾
1 · How it flows
Shortlist of nearby providers (from feature 03)
→
Pull rating, experience, reliability, distance, availability per provider
→
Compute a score for each
→
Sort providers highest score first
→
Show ranked list to user
2 · Tools & concepts (explained simply)
Weighted scoring formulaFree — your own logic

Start simple: score = (w1 × rating) + (w2 × experience) + (w3 × reliability) − (w4 × distance) + (w5 × availability). You choose the weights (w1...w5) based on what should matter most. This is fully transparent and easy to explain in your report — always start here before anything fancier.

Bayesian average (for the cold-start problem)Free — a formula

A brand-new provider with one 5-star review shouldn't outrank an experienced provider with 100 reviews averaging 4.7. A Bayesian average "pulls" new providers' scores toward the platform's overall average until they build up enough reviews to be trusted — a well-known Data Science technique worth naming explicitly in your report.

scikit-learn / LightGBM learning-to-rank model (advanced/optional)Free

Once you have some real or simulated booking history, you can train a model that learns which factors actually predict a successful, well-rated job — rather than you guessing the weights by hand. This is a genuine machine-learning ranking system, and including it (even as a stretch goal) is the single biggest "impress the evaluators" upgrade for this feature.

3 · Alternatives & what to actually pick
Recommended: build the weighted formula first, then add a learn-to-rank model as your "advanced" showcase

A pure hand-tuned formula is easy but purely rule-based — fine for an MVP, less exciting for a Data Science evaluation. A full learning-to-rank model (LightGBM Ranker/XGBoost) is the closer-to-industry approach (similar in spirit to how e-commerce and ride-hailing platforms rank results) and is very demo-able: you can literally show a chart comparing "before ML ranking" vs "after ML ranking" match quality.

4 · Edge cases to plan for
  • New provider, no reviews yet — handled by the Bayesian average, not by ignoring them entirely.
  • Tied scores — break ties using distance or availability as the deciding factor.
  • Fake or inflated ratings — flag providers with unusually fast bursts of 5-star reviews for manual review.
  • All top-ranked providers unavailable right now — still show them but visibly mark availability and re-rank by who can actually come sooner.
05 Agent-Based Assistance ▾
1 · How it flows
User sends a message describing their situation
→
Agent detects intent (book / ask / complain / cancel)
→
Agent extracts entities (category, urgency, location)
→
Agent asks a follow-up question if info missing
→
Agent hands off to matching/booking engine
2 · Tools & concepts (explained simply)
Rasa Open SourceFree, self-hosted

Rasa is a free framework specifically built for making chat agents: it handles "what does the user want" (intent classification) and "what information do I still need from them" (dialogue management/slot filling), all running on your own machine — no per-message fee, and you fully own the logic, which is exactly what a Data Science evaluator wants to see you build.

spaCyFree

Used to pull out specific useful pieces of information from a sentence — like spotting "kitchen sink" as a location detail or "urgent" as a priority flag — a concept called Named Entity Recognition. It works alongside Rasa or on its own.

A hosted LLM API (Anthropic/OpenAI) — optional add-on onlyAPI — only where truly needed

If you want the agent to handle completely open-ended, free-form conversation beyond your trained intents (e.g., unusual questions), a large language model API is genuinely hard to replace with student-built tools. Keep this as a clearly-labelled fallback layer, not the whole agent, so your report shows what you engineered yourself versus what you responsibly outsourced.

3 · Alternatives & what to actually pick
Recommended: Rasa + spaCy as the core agent, LLM API as a documented fallback only

Using only an LLM API for the whole agent is the easiest route, but risks looking like "I made an API call" rather than "I built an intelligent agent" — evaluators specifically watch for this in Data Science/AI projects. Google Dialogflow is a decent alternative but is fully cloud/API-dependent by design, which goes against the brief. Rasa lets you genuinely train and evaluate your own intent classifier (with accuracy scores you can report), which is much stronger portfolio material.

4 · Edge cases to plan for
  • Ambiguous or vague input — the agent should ask a clarifying question rather than guessing wrong.
  • Requests outside the app's scope — politely redirect instead of pretending to help.
  • Repetitive confusion loops — after 2–3 failed clarifications, offer a "talk to human support" / manual category selection escape hatch.
  • Typos and slang — include varied, informal training examples so the model doesn't only work on textbook sentences.
06 Communication Between User and Service Provider ▾
1 · How it flows
User/provider open chat screen
→
WebSocket connection opens with server
→
Message sent instantly to the other person
→
Message saved to database
→
Push notification if recipient is offline
2 · Tools & concepts (explained simply)
WebSockets (via FastAPI's built-in WebSocket support, or Socket.io)Free, self-built

A normal web request is like sending a letter and waiting for a reply — slow for chat. A WebSocket is like an open phone line: once connected, both sides can send messages instantly, back and forth, without reconnecting each time. This is the real technology behind every chat app.

PostgreSQL/MongoDB chat history tableFree

Even though messages travel instantly, you still save every message to a database so the conversation isn't lost if someone closes the app and reopens it later.

Simple profanity/abuse filter (word-list based, e.g. better-profanity library)Free

A basic safety net that scans outgoing messages for obviously abusive language before they're sent, protecting both users and providers.

3 · Alternatives & what to actually pick
Recommended: self-built WebSocket server

Firebase Realtime Database/Firestore is very quick to set up but is entirely dependent on Google's service — it teaches you the "what" but not the "how" of real-time systems. Building your own WebSocket server demonstrates genuine backend systems knowledge, which stands out far more to a hiring engineer than "I connected to Firebase."

4 · Edge cases to plan for
  • Recipient offline — queue the message and deliver it (plus a notification) when they reconnect.
  • Network drops mid-chat — auto-reconnect the WebSocket and resend any unsent messages.
  • Message ordering — timestamp every message server-side so order is always consistent, even under lag.
  • Large file/image sharing — enforce a file size limit and show upload progress.
  • Abusive messages — filter + allow reporting, with a manual review queue.
07 Booking and Scheduling ▾
1 · How it flows
User views provider's available time slots
→
User picks a date & time
→
Backend checks for scheduling conflicts
→
Booking confirmed & saved
→
Confirmation sent to both sides
2 · Tools & concepts (explained simply)
react-datepicker / calendar UI componentFree, open-source

A ready-made, free calendar widget so users don't have to type dates manually — reduces bugs and looks professional immediately.

Database transactions with unique constraintsFree — a DB concept

To stop two users from booking the exact same provider slot at the exact same time, you use a database "transaction" — a rule that says "check and book in one uninterruptible step," so two requests can never both succeed for the same slot.

3 · Alternatives & what to actually pick
Recommended: self-built scheduling logic, with Google Calendar sync as an optional bonus

Relying purely on Google Calendar API for scheduling logic makes your core feature dependent on an external service for something you can absolutely build yourself with database rules. Build the core booking/conflict logic yourself, and optionally add a "sync to my Google Calendar" export button as a nice-to-have — this shows you know when an API is a genuine convenience add-on versus a core dependency.

4 · Edge cases to plan for
  • Double booking — prevented using a database transaction/lock on the time slot.
  • Last-minute provider cancellation — notify the user immediately and auto-suggest the next best available provider.
  • Time zone differences — store all times in UTC internally, convert only for display.
  • No-shows — track no-show counts and factor them into the provider's reliability score (feature 04).
  • Rescheduling requests — allow edits up to a cutoff time, then require cancellation + rebooking instead.

2 · Tools & concepts (explained simply)
Browser Geolocation API (same as feature 03)Built-in, free

Reused here on the provider's side of the app to continuously report their position during an active job.

Same WebSocket server (reused from feature 06)Free

You don't need a separate system — the same real-time connection technology that powers chat also pushes live location updates, keeping your architecture simple.

Leaflet.js live marker updatesFree

The map you already built for provider matching is reused here — instead of static pins, the provider's pin now moves in real time as new coordinates arrive.

Recommended: Leaflet + WebSockets, exactly as used in earlier features

Google Maps' live tracking widgets look polished but come with per-load billing at scale. 4 · Edge cases to plan for
  • GPS/network signal lost — show "last known location" with a timestamp instead of freezing silently.
  • Provider forgets to start tracking — provide a manual "I've arrived" status button as a fallback.
  • Battery-saving mode limits updates — reduce update frequency gracefully rather than failing.
  • Privacy — only share live location while a job is actively in progress, never continuously.
09 Ratings and Reviews ▾
1 · How it flows
Job marked complete
→
User prompted for star rating + written review
→
Review text checked for sentiment & abusive language
→
Stored, provider's average rating recalculated
2 · Tools & concepts (explained simply)
VADER / TextBlob sentiment analysisFree, open-source

These are ready-made Python tools that read a review's text and estimate whether it sounds positive, neutral, or negative — useful for automatically flagging a written review that says something very negative even if the star rating given was oddly high (a mismatch worth a human's attention).

better-profanity library (or a simple word-list filter)Free

Automatically blocks or masks offensive language in submitted reviews before they're published publicly.

Bayesian average (reused from feature 04)Free — a formula

Keeps a provider's overall star rating fair even with very few reviews so far, instead of letting one review swing it wildly.

3 · Alternatives & what to actually pick
Recommended: VADER/TextBlob sentiment analysis + Bayesian averaging

Manual moderation only (a human reads every review) doesn't scale and shows no Data Science work. Adding automated sentiment analysis and profanity filtering is inexpensive, genuinely useful, and gives you a natural NLP section to include in your report — you can even show an evaluation of how accurately your sentiment tool agrees with the star rating given.

4 · Edge cases to plan for
  • No review submitted — still count the completed job, just without written feedback.
  • Review bombing — detect unusual bursts of extreme ratings in a short time window and flag for review.
  • Sentiment vs. star rating mismatch — flag reviews where the text sounds very negative but the star rating is high (or vice versa).
  • Disputed ratings — allow a formal dispute/appeal process rather than letting one bad rating be permanent and unquestionable.
10 Service History ▾
1 · How it flows
User/provider opens "History" tab
→
Backend queries DB filtered by their id, paginated
→
List displayed with filters (date, category, status)
2 · Tools & concepts (explained simply)
Database indexingFree — a DB concept

An index is like the index at the back of a textbook — it lets the database jump straight to a user's records instead of scanning the entire table, keeping history loading fast even with thousands of bookings.

Pagination (LIMIT/OFFSET or cursor-based)Free — a backend concept

Instead of sending a user's entire history at once, the backend sends it in small pages (e.g. 20 records at a time) as the user scrolls — much faster and lighter on the app.

3 · Alternatives & what to actually pick
Recommended: plain indexed SQL queries with pagination

Elasticsearch is what large companies use for lightning-fast search across millions of records, but it is overkill for a student project's data size. Mentioning in your report "at production scale, this could migrate to Elasticsearch" shows awareness of how real systems evolve, without over-engineering your actual build.

4 · Edge cases to plan for
  • Very long history — always paginate, never load everything at once.
  • Deleted/inactive accounts — soft-delete (mark as inactive) rather than erasing records outright, to preserve audit/history integrity.
  • Filters returning nothing — show a friendly empty state rather than a blank screen.
  • Exporting history — a nice optional extra: let users download their history as a PDF using a free PDF-generation library.
11 Provider Dashboard ▾
1 · How it flows
Provider logs in
→
Dashboard loads bookings, ratings, earnings
→
Provider toggles availability / updates schedule
→
Charts display performance trends over time
2 · Tools & concepts (explained simply)
Plotly (or Chart.js) for the frontend chartsFree, open-source

Turns raw numbers (jobs completed per week, average rating over time, earnings) into visual charts. Plotly is more interactive and has a stronger "Data Science" feel, which fits nicely with your academic background.

SQL aggregate queries (GROUP BY, AVG, COUNT)Free — a DB concept

The database itself calculates things like "average rating this month" or "total jobs completed" directly, rather than pulling every row into Python and calculating it there — much faster and is a core SQL skill worth demonstrating.

3 · Alternatives & what to actually pick
Recommended: Plotly for the dashboard visuals

Chart.js is lighter and simpler, a fine choice if you're short on time. Plotly produces richer, more interactive charts (zoom, hover tooltips) and is a library Data Science evaluators will immediately recognize and respect, since it's widely used in real analytics work.

4 · Edge cases to plan for
  • Provider with no bookings yet — show an encouraging empty state, not a broken chart.
  • Marked unavailable mid-booking — must still complete any already-confirmed bookings before going fully offline.
  • Overlapping availability edits — validate new availability windows against existing bookings before saving.
  • Earnings calculation errors — use database transactions so an earnings update can never be partially applied.

Your step-by-step roadmap
Phase 1 · Weeks 1–2

Plan before you code

Write down your exact database tables (Entity-Relationship diagram), sketch your screens on paper or in Figma, and write one clear sentence for what each of the 11 features must do. Skipping this step is the #1 reason student projects fall apart halfway through — 30 minutes of planning saves 5 hours of confused rewriting later.

Phase 2 · Weeks 3–4

Build the foundation: registration, login, and the database

Get a user able to sign up, log in, and see an empty dashboard before anything else. This proves your whole chain — frontend, backend, database — is actually connected correctly.

Phase 3 · Weeks 5–7

Core marketplace loop: request → match → rank → book

Build service request creation, nearby matching, and ranking together, since they naturally feed into each other. At this stage your app should already let a fake user "find and book" a fake provider end-to-end, even with rough styling.

Phase 4 · Weeks 8–9

Real-time features: chat, live tracking, and the agent

These are technically the hardest, so build them once your core loop already works — don't attempt everything at once. Get chat working first, then reuse that same WebSocket connection for tracking.

Phase 5 · Weeks 10–11

Ratings, history, and the provider dashboard

These features depend on there being some data already in your system, so build them after you have test bookings to actually display.

Phase 6 · Weeks 12–13

Polish, test, evaluate your models, and write it all up

This phase is where a "working app" becomes an "impressive final year project" — see the tips below for exactly what to focus on here.

How to make this project genuinely stand out
1

Prove your models actually work

Don't just say "I used a classifier." Report its accuracy, precision, and confusion matrix on a held-out test set. Numbers turn "I used ML" into "I evaluated ML" — that difference is exactly what separates an average project from an excellent one.

2

Keep a clean, well-organized GitHub repo

A clear README with setup instructions, screenshots, and an architecture diagram is often the very first thing a recruiter or evaluator looks at — before they even open your code.

3

Deploy a live demo link

Even a slightly slow free-tier deployment beats "you'll have to run it locally to see it work." Being able to hand someone a link changes how seriously they take your project.

4

Write a short project report alongside the code

Cover: the problem you're solving, why you chose each tool (you now have this whole document for that!), your system architecture, your model evaluation results, and what you'd improve with more time. This becomes your thesis document almost for free.

5

Record a short demo video

A 3–5 minute walkthrough of the whole app working end-to-end is incredibly persuasive in interviews and presentations, and it protects you if something breaks live during your defense.

6

Test as you go, not at the end

Use pytest for backend logic and Postman/Thunder Client to manually check your APIs as you build each feature — catching a bug the day you wrote it is far easier than catching it three features later.

7

Start with an MVP, then layer on the "smart" parts

Get a bare, ugly version of every feature working first, end-to-end. Only after that should you go back and add the ML ranking model, sentiment analysis, and polish. A fully working simple app beats a half-working fancy one, every time.

8

Use a project board to track yourself

A free Trello or Notion board with your 11 features broken into small tasks keeps you honest about progress and looks great if you show it during your viva as evidence of a structured process.

One last thing, honestly: you don't need to build all 11 features at their most advanced version to succeed. A working core (registration, request creation, matching, ranking, booking) with two or three features pushed to an impressive, evaluated, ML-backed level will beat a shallow attempt at all eleven. Pick your "showcase" features — I'd suggest the classifier in feature 02, the ranking model in feature 04, and the agent in feature 05 — and make those genuinely excellent.

You've never built an app before, and that's completely fine — everyone's first real project feels overwhelming at the start. Follow the roadmap phase by phase, don't skip the planning week, and ask for help (from me, your advisor, or documentation) the moment you're stuck for more than an hour. That's not a weakness, that's exactly how real engineers work too.
